# Robust capture patterns from current source code — 20 October 2026

## Scope and source snapshot

This note compares LinkX's slow browser-tab observation demo with two live implementations: ShareX's Windows scrolling screenshot stitcher and screenpipe's screenshot change detector and event-driven capture loop. I inspected source at ShareX `10a74d50a29229a31b5a68e61acf8130403edba2` (`develop`, committed 2026-10-20) and screenpipe `315ac4a99ef47729a820eab333dda8ca32e6fbe5` (`main`, committed 2026-10-20). Links below are pinned to those revisions. The current screenpipe source is authoritative for behavior; its event-driven capture spec says it was last checked on 2026-02-20 and warns that names and thresholds have since changed ([historical spec warning](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/docs/EVENT_DRIVEN_CAPTURE_SPEC.md#L1-L7)).

LinkX currently receives a user-selected shared-tab video stream and samples its pixels. The v2 protocol explicitly excludes production DOM, accessibility, CDP, navigation, and input access; it records stream frame delivery separately from sampler decisions and asks for actual before/after pixels for the controlled `44`→`45` change ([v2 protocol](./automatic-capture-v2/PROTOCOL.md#surfaces-and-privacy-boundary), [measurements and analysis order](./automatic-capture-v2/PROTOCOL.md#measurements)). In the observation-lab's v1 sampler, 32×32 RGBA thumbnails are the default; it evaluates 8×8 tiles and requires at least 8% of a tile's pixels to exceed a channel delta of 24. It waits for a persistent settled change and suppresses an exact repeat of the accepted thumbnail ([sampler defaults and tile test](../../../frontend/scripts/observation-lab/automatic-capture-v1/sampler.mjs#L1-L12), [settle and duplicate decision](../../../frontend/scripts/observation-lab/automatic-capture-v1/sampler.mjs#L90-L140), [candidate decision](../../../frontend/scripts/observation-lab/automatic-capture-v1/sampler.mjs#L220-L229)). This lab sampler evaluates settled localized thumbnail changes and exact repeats. Its downsampled tile gate can still miss a small glyph change before a full-size candidate is encoded.

## What ShareX implements

ShareX drives scrolling itself with mouse-wheel, arrow, Page Down, or Windows scroll messages, then captures a selected desktop rectangle after each step ([scroll inputs and capture loop](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L121-L167)). It incrementally extends the composite instead of retaining all source images until the end. For each incoming image, it searches the previous composite's lower viewport-sized band for a row-aligned overlap with the new image. It compares exact pixel scanlines across the central horizontal region, ignoring side margins that may contain scrollbars or other noisy edges ([overlap search setup and row matching](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L255-L329)).

The stitcher also allows a bottom band to be omitted: with `AutoIgnoreBottomEdge`, it scans for a mismatch between the composite and new frame's bottom rows, grows the ignored band, and keeps the largest previously observed band. It then appends only the rows below the detected overlap. This is a pragmatic defense against a fixed bottom strip covering moving content; it is not a general sticky-header detector ([bottom-band handling and append](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L284-L363)).

ShareX remembers its best overlap. If a later frame has no valid overlap, it can reuse that earlier alignment but changes the result status to `PartiallySuccessful`; if no alignment exists, it fails. That visible uncertainty is a useful pattern: low-confidence geometric reconstruction should be reported as incomplete rather than silently treated as complete ([fallback and status](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L331-L380)). The current loop stops after consecutive captured images compare equal ([end check](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L121-L128), [comparison](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L240-L248)). A Windows scrollbar-bottom helper is also present in the file but not called by this loop ([helper](https://github.com/ShareX/ShareX/blob/10a74d50a29229a31b5a68e61acf8130403edba2/ShareX.ScreenCaptureLib/ScrollingCaptureManager.cs#L226-L238)).

These are useful mechanisms for actual full-page stitching, but most do not transfer to LinkX's passive video stream. LinkX does not send scroll input, know the scroll step, know the source rectangle, or know whether a repeated strip is a sticky control or real page content. A global overlap stitcher could merge unrelated view changes and would turn current-view context into an inferred page archive. The transferable part is to treat relative vertical displacement as a confidence-scored estimate and use it to describe coverage or detect a likely repeated view; each accepted current-view screenshot should stay independently usable.

ShareX has an open feature request proposing dynamic-region detection by comparing two frames and masking stationary pixels. It is a user proposal, not implemented behavior, and its stated failure mode is sticky sidebars, headers, and footers ([ShareX issue #8631](https://github.com/ShareX/ShareX/issues/8631), opened 2026-05-15). The suggested exact-zero difference mask would also confuse static page regions with content that happened not to change in that pair; it should not be copied as a reliable segmentation algorithm.

## What screenpipe implements now

Current screenpipe uses a proportional 1/4-resolution thumbnail for comparison. Its downscale is direct point sampling: for each thumbnail location it reads one source pixel, records that pixel's RGBA in a hash, and stores its grayscale intensity. The maintainer comment records that factor 6 caused hash collisions on dense text pages and made log scrolling invisible; factor 4 is the current compromise ([configuration and documented failure](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-screen/src/frame_comparison.rs#L89-L115), [point-sampled thumbnail](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-screen/src/frame_comparison.rs#L150-L194)).

It first compares the thumbnail's RGBA hash for an exact fast exit. When the hash differs, the default high-performance configuration compares grayscale histograms; optional mode averages histogram difference and SSIM. The comparison module is explicitly an optimization gate, not the stored OCR input ([hash early exit and comparison](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-screen/src/frame_comparison.rs#L217-L320)). The external visual-change threshold is 0.05 and the default visual probe interval is three seconds ([current event-driven config](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-engine/src/event_driven_capture.rs#L555-L605)); probe code turns only a comparison score above that threshold into a `VisualChange` capture trigger ([active visual probe](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-engine/src/event_driven_capture.rs#L1935-L1955)).

This is a good CPU-saving pattern for broad visual changes and exact repeats. It does not provide a safe sole detector for a tiny text change: a point-sampled thumbnail may miss the changed strokes, and a histogram does not preserve their location. A hash hit is exact only for the sampled pixels, not for every source pixel. The available current tests demonstrate major full-screen changes and large content-pattern changes; they do not establish sensitivity for a small digit or thin glyph ([current comparison tests](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-screen/src/frame_comparison.rs#L599-L624)).

Screenpipe also triggers capture from app/window focus, clicks, typing pauses, scroll stops, keyboard and clipboard events, then debounces and applies an idle fallback. Its current enum documents those triggers, including visual changes for animation or auto-scroll ([trigger types](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-engine/src/event_driven_capture.rs#L340-L380)). Those event paths are unavailable to a browser page merely shared through `getDisplayMedia`; LinkX has to infer change from sampled frames and the stream's own frame-delivery metadata. The stale spec's statement that frame comparison became idle-only dedup must not be repeated as current behavior.

## Recommendation for the slow research demo

Keep the demo's scope as settled, distinct viewport candidates, with no source-page stitching. Add no model concurrency. Keep the fixed sample cadence and latest-pending bound already specified. Use low-resolution tiles to estimate motion and decide when a view has settled, but let a small, persistent high-resolution pixel change become a candidate even when its thumbnail or global changed-area score is small. Do not let an exact hash of a reduced image veto that high-resolution check. Store the actual full-resolution candidate pixels; use thumbnails only for bounded comparison and preview.

The smallest robust demo contract is:

1. **Source validity:** a controlled marker appears in the shared-tab stream, and video callback/presented-frame counters advance across each controlled source change. Otherwise classify the run as invalid or stale before judging image thresholds.
2. **Small-change sensitivity:** a single controlled `44`→`45` change yields one candidate containing the new digit after the configured settle interval, even though the changed region occupies a tiny fraction of the viewport. Retain source-stream PNGs and matching thumbnails for inspection.
3. **Scrolling and settling:** cover rapid fling, slow reading, small increments, reversal, pause, zoom, and a separate animation case. Report where a candidate was missed or delayed; avoid claiming page coverage from frame cadence alone.
4. **Bounded behavior:** retain no more than one pending candidate and record a gap when it is replaced; keep per-sample decisions and candidate bytes so dedup, missed changes, and queue pressure remain distinguishable.

These criteria extend the prospective v2 protocol's own scenario and measurements rather than treating one demo pass as validation of all browser pages ([protocol scenarios](./automatic-capture-v2/PROTOCOL.md#predeclared-scenarios), [boundedness and validity](./automatic-capture-v2/PROTOCOL.md#boundedness-and-validity)). The first useful experiment remains the protocol's order: inspect whether the digit survives source pixels and thumbnail pixels before tuning a threshold, then separate stale delivery from a gating miss. If thumbnail pixels lost it, test a localized multiscale comparison; if full-size source pixels lack it, investigate stream delivery or sampling.

## Failure modes to report

- **Thin glyph or small counter change:** direct point downscaling can skip changed strokes; a global score can dilute them. Require the controlled pixel pair and count candidate misses.
- **Sticky or animated regions:** a fixed region can keep moving even while the article settles; a global motion gate can then starve candidates. Evaluate stable changed tiles individually, as LinkX already does, and add a test where unrelated animation persists beside the changed text.
- **Fast scroll or direction reversal:** sparse sampling can skip intermediate viewports. Report coverage gaps; do not reconstruct a complete long page from guessed overlaps.
- **Dynamic content and reflow:** images, lazy loading, font changes, responsive layout, and zoom can change many pixels without corresponding to vertical scroll. Reset relative-motion estimates on dimension/zoom changes and avoid using overlap as an absolute position.
- **Static viewport:** identical frames are safe duplicates only when source delivery is verified current. Keep media time/callback counters so a frozen stream is not misclassified as an unchanged page.
- **Resource pressure:** screenpipe explicitly treats thumbnail-allocation failure as unchanged to avoid an expensive OCR path ([failure branch](https://github.com/screenpipe/screenpipe/blob/315ac4a99ef47729a820eab333dda8ca32e6fbe5/crates/screenpipe-screen/src/frame_comparison.rs#L222-L240)). A demo should expose sampler/encoding failures as gaps instead of silently counting them as successful deduplication.

The full-page overlap alignment, bottom-edge trimming, OS scroll input, and fallback composite status in ShareX remain platform- and task-specific. The actionable lesson for LinkX is confidence and explicit gaps around inferred movement, while preserving each full-size settled viewport capture as the ground truth.
