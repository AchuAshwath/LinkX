# Robust screen registration for a sequential shared-tab demo — 20 October 2026

## Decision

Use a **serial capture → register → classify → interpret** loop. Preserve every admitted viewport frame with its capture time and sequence number. Estimate relative positions between adjacent stable frames, but only join frames into a coverage segment when registration passes explicit confidence gates. Keep the original viewport images and a compact chronological coverage ledger; do not make one large stitched image the only record. A low-confidence pair starts a new segment and records an unknown gap. The demo can interpret admitted frames one at a time; do not add parallel model generation or make correctness depend on a future speed optimization.

This is a proposed design based on image-registration methods and the local tuning evidence. It has **not** been implemented or measured on browser screenshots. Proposed thresholds below must be calibrated on labeled screen captures; papers and API docs do not establish browser-specific cutoffs.

## Evidence and limits

The local v2 run captured three long articles at the shared video’s native 2880×1550 pixels. Its sampler accepted 178 candidates from 839 samples over roughly 209 seconds, or about 0.85 candidates/second. The report explicitly says candidate counts do not measure semantic recall or OCR accuracy, representative frames were only visually reviewed, the telemetry lacks independent frame hashes, and zoom/reflow was not tested. One controlled 44→45 change was retained, but that result supports that case only. These are the relevant baseline facts, not evidence that stitched coverage already works. [Tuning v2 report](combined-v1/TUNING-V2-REPORT.md) [Tuning v2 protocol](combined-v1/TUNING-V2-PROTOCOL.md)

Ordinary shared-tab pixels contain no authoritative document scroll position or page height. The existing local research note establishes that limitation from the browser capture API surface. Any position produced here is therefore relative and estimated from pixels. [Browser sharing metadata and capture options](browser-sharing-metadata-and-capture-options-2026-10-20.md)

## Registration methods that fit the problem

A browser tab that scrolls mostly vertically is closer to a document scan than a camera panorama. Start with a constrained **vertical translation** estimate over shared content. OpenCV’s `phaseCorrelate` is explicitly for translational shift detection and returns a response in `[0, 1]`; the documented response summarizes the correlation peak and falls when there are multiple peaks. It uses a Hann window and a Fourier-domain shift estimate. This is a useful inexpensive first estimate, but its response is a signal-quality indicator, not a calibrated probability that a browser pair is correctly aligned. [OpenCV `phaseCorrelate` documentation](https://docs.opencv.org/4.5.1/d7/df3/group__imgproc__motion.html)

For local capture, apply phase correlation to the stable content region after excluding likely browser chrome and sticky overlays. Prefer a vertical search over masked overlap bands rather than letting a full-frame score be dominated by fixed headers. Compare several horizontally separated bands: a genuine scroll should yield compatible vertical shifts in those bands. A distinctive text line or icon should not be allowed to establish the offset alone. These masking, band-agreement, and duplicate-text safeguards are browser-specific design hypotheses; validate them with labeled captures.

Use **ECC alignment** only as a refinement after a plausible coarse estimate. OpenCV documents translation, Euclidean, affine, and homography models, and notes that larger displacements need a roughly correct initialization; it can throw when it does not converge. For normal scrolling, begin with translation. Permit a scale or affine model only when the viewport appears zoomed or reflowed and there is enough shared textured content. Do not accept a high-flexibility transform simply because it can warp unrelated paragraphs into a high score. [OpenCV `findTransformECC` documentation](https://docs.opencv.org/4.0.0/dc/d6b/group__video__track.html) [Evangelidis and Psarakis, *Parametric Image Alignment Using Enhanced Correlation Coefficient Maximization* (2008)](https://www.researchgate.net/profile/Emmanouil-Psarakis/publication/23171525_Parametric_Image_Alignment_Using_Enhanced_Correlation_Coefficient_Maximization/links/09e41512d0d8ea67c8000000/Parametric-Image-Alignment-Using-Enhanced-Correlation-Coefficient-Maximization.pdf)

When translation correlation is ambiguous, use local feature correspondences and a robust fit as a fallback. OpenCV’s feature-homography tutorial uses matched keypoints with `findHomography` and RANSAC to reject false correspondences. The original RANSAC paper describes fitting despite a significant share of gross errors in feature data. For a document-like browser viewport, constrain the fallback to the simplest plausible model: translation or similarity/partial affine first; reserve homography for capture geometry that actually requires it. Record inlier count, inlier fraction, spatial spread, and residual error. RANSAC rejects outliers but cannot make repeated paragraphs unique; duplicated headers and repeated text can still produce a coherent wrong match. [OpenCV feature matching and homography tutorial](https://github.com/opencv/opencv/blob/5.x/doc/tutorials/features/feature_homography/feature_homography.markdown) [Fischler and Bolles, *Random Sample Consensus* (1981)](https://www.cs.cmu.edu/~motionplanning/papers/sbp_papers/f/p381-fischler.pdf)

`matchTemplate` is another option for a small, distinctive crop. OpenCV describes it as sliding a template over a source and locating the best score. It is useful for checking whether a proposed shared patch exists at a particular offset, but a single maximum is not enough: repeated lines can create equally good matches. Compare the best and next-best separated peaks and require agreement from another region before joining a pair. [OpenCV template-matching tutorial](https://docs.opencv.org/5.0/tutorials/imgproc/histograms/template_matching/template_matching.html)

## Practical handling of browser-specific failure cases

- **Sticky headers and fixed controls:** Keep them in each viewport image, but mask them from scroll registration if they remain at a stable screen coordinate. Detect the mask conservatively from pixels across several frames. If the mask is uncertain, rely on content bands lower in the viewport. Do not use the header as evidence that the document position did not change.
- **Repeated paragraphs or repeated cards:** Require separated regions to agree on the same shift, a clear best-match margin over competing offsets, and a plausible shift direction/magnitude relative to the immediately preceding frame. If the page contains repeated content, a pair can be ambiguous even with many matches; preserve it as a separate segment when the ambiguity remains.
- **Dynamic counters, clocks, cursors, and animations:** Use a robust/local score so a few changed blocks do not dominate the alignment. Keep those pixels in the original viewport and run change detection separately; masking a dynamic region for registration must not erase its change from the retained evidence.
- **Reverse scrolling:** Add every frame in capture order. A reverse transition is a new observation at an estimated previously seen location, with a new timestamp; it does not reorder the timeline. Infer direction only when the aligned content shift is confident. If the pair is uncertain, retain a new segment instead of snapping it to an older location.
- **Zoom, resize, and responsive reflow:** A video dimension change is already treated locally as a sampler reset with an explicit gap. Extend the same conservative boundary to strong scale/layout changes detected inside constant-sized frames: start a new geometry epoch, keep the frame, and attempt scale-aware matching only with sufficient support. Reflow can change line wrapping without a single global transform, so an affine fit is not a license to bridge the change.
- **Little or no overlap:** No registration method can recover content that appears in no retained frame. Do not extrapolate an absolute page offset or imply continuous coverage. Preserve the nearest viewport frames and a gap marker with the time interval and reason (`low-overlap`, `low-confidence`, `geometry-change`, or `sampling-gap`). A later frame may reconnect to an earlier segment if independent evidence passes the same gates.
- **Selection and OCR:** Preserve useful stable views and visible changes; do not discard a frame solely because it resembles its predecessor before alignment. The `psc2code` study is relevant as adjacent evidence: its programming-screencast pipeline filters unusable frames and uses cross-frame OCR information, but its evaluated domain is programming videos/code regions. Its reported F1 and search precision apply to that dataset and task, not browser articles or this capture design. [Bao et al., *psc2code: Denoising Code Extraction from Programming Screencasts*](https://arxiv.org/abs/2103.11610)

## Confidence gates and measurable evaluation

Store confidence as components so a reviewer can see why a pair was accepted: valid overlapping area; phase-correlation response and peak margin; estimated shift; agreement among spatially separated bands; feature-match inlier count/fraction and spatial spread when used; ECC convergence and final correlation when used; and residual error after warping. Keep model type and geometry epoch with each relation. A single library score must never stand in for all of these checks.

Use a labeled evaluation set containing slow/tight/fast/reverse scroll, repeated paragraphs/cards, persistent sticky regions, changing digits, animation, zoom, resize/reflow, and deliberate jumps that remove overlap. Include known offsets only in the test harness as ground truth; the running capture path continues to receive shared-tab pixels only. Report at least: accepted-pair false-registration rate; rejected-pair rate; shift error in pixels; fraction of frames linked to a segment; uncovered time/estimated content spans; duplicate-coverage rate; small-change retention; and p50/p95 registration time. Score registrations against independent ground truth, not the registration method’s own confidence score.

Calibrate gates on held-out pairs. As an initial experiment, require a unique offset peak, agreement from at least three separated content bands when those bands exist, and a minimum overlap fraction; record failures rather than loosening thresholds to make every pair join. The values for “unique,” band tolerance, minimum overlap, inlier counts, and residual bounds are hypotheses until calibrated. A useful acceptance target is zero false joins on a predeclared adversarial repeated-text set, with ambiguous pairs explicitly rejected; publish both this result and the useful-link rate so the system cannot look reliable by rejecting everything.

## Capture and presentation policy for the slow demo

1. Keep the existing shared-tab video-and-canvas capture source. On each stable candidate, save the original viewport image, capture time, monotonic sequence number, dimensions, and change reason.
2. Process one candidate at a time. Compare it to its adjacent stable predecessor; estimate registration, then either append a high-confidence relative edge or open a new segment and log the gap. Do not call the model while another generation is in flight.
3. Maintain a bounded chronology-preserving record: recent viewport frames, representative anchor frames per connected segment, and a compact segment/coverage ledger. Keep original frames as evidence for any derived coverage view. Avoid using one ever-growing stitched raster as the source of truth; it duplicates pixels, compounds alignment drift, and obscures missing spans.
4. In the demo, show the timeline and viewport frames. If a small coverage strip is useful, render it per connected segment and visibly mark unknown gaps and confidence. Never fill a gap by stretching neighboring content or treat estimated coordinates as document scroll positions.

This serial path is intentionally paced for the research demo. The local report measured about 0.85 accepted candidates/second against separate model workloads averaging about 0.178 image interpretations/second for five synthetic calls, with one real article interpretation taking 12.847 seconds. Those measurements are different workloads, and the scroll matrix had no model calls; they establish neither a production throughput nor a queue policy. They do show why the demo should not promise real-time interpretation of every candidate. [Tuning v2 report](combined-v1/TUNING-V2-REPORT.md)

Avoid using FFmpeg `mpdecimate` as the capture-admission rule. Its documented drop decision considers 8×8 blocks and a `frac` threshold; its default `frac` is 0.33. A tiny but meaningful digit or badge change can affect far fewer blocks than the frame-level threshold, so a duplicate-video filter can classify the changed frame as similar. This is a risk inferred from the documented block threshold, not a measured result on the LinkX fixtures. [FFmpeg `mpdecimate` documentation](https://www.ffmpeg.org/ffmpeg-filters.html#mpdecimate)
