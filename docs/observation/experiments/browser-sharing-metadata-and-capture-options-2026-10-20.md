# Browser sharing metadata and capture options — 20 October 2026

## Finding

Ordinary browser screen sharing does not automatically expose a page URL, DOM, scroll offset, or document height to the capturing web app. `getDisplayMedia()` gives the app a user-selected display surface as a media stream; the Screen Capture specification's track settings cover capture properties such as `displaySurface`, `logicalSurface`, `screenPixelRatio`, and the ordinary video settings such as width, height, and frame rate. None describes the captured document's location or geometry. The standard also says the user chooses a surface for each `getDisplayMedia()` call. [W3C Screen Capture](https://www.w3.org/TR/screen-capture/)

`HTMLVideoElement.requestVideoFrameCallback()` provides frame delivery and timing metadata (including frame dimensions, media time, presentation time, and presented-frame count), not source-page state. `ImageCapture.grabFrame()` snapshots one frame from its `MediaStreamTrack` into an `ImageBitmap`; it does not produce a full-page image or add page metadata. [WHATWG HTML Standard: video frame callbacks](https://html.spec.whatwg.org/multipage/media.html#dom-video-requestvideoframecallback), [W3C MediaStream Image Capture](https://www.w3.org/TR/image-capture/)

That means a capture app can infer that the displayed pixels changed, and can compare overlap between adjacent frames to estimate relative movement when page content is stable. It cannot get an authoritative absolute scroll position or total page height from those pixels. Sticky elements, animation, reflow, lazy-loaded content, and nested scroll containers can make overlap-based estimates ambiguous. This is an inference from the pixel-only input and the API surface above, not a guarantee made by the specifications.

## Capture choices

| Method | What it can provide | Limits and requirements |
| --- | --- | --- |
| **Ordinary `getDisplayMedia()` stream** | Repeated snapshots of the shared tab's visible rendered viewport. Use the video element and canvas for sampling; `requestVideoFrameCallback()` can schedule work when frames arrive. `ImageCapture.grabFrame()` is another snapshot path from the same visible track. | No page URL, DOM, scroll offset, or document height. `getSettings()` and frame callback metadata describe the captured media, not the source page. A normal user share remains manually browsed and pixel-only. [Screen Capture](https://www.w3.org/TR/screen-capture/), [HTML video frame callback](https://html.spec.whatwg.org/multipage/media.html#dom-video-requestvideoframecallback), [Image Capture](https://www.w3.org/TR/image-capture/) |
| **Captured Surface Control** | In supported Chrome, a capturing app can forward wheel input to a captured tab and read or change that tab's zoom. | This controls a shared tab; it is not scroll-position telemetry. `forwardWheel()` relays wheel events from an element in the capturing app to the captured tab. Chrome documents availability from Chrome 136 on desktop. The first use of wheel forwarding or zoom controls prompts for permission and must be initiated from a user gesture. This may move the user's page, so it does not passively report where the user has scrolled. [Chrome for Developers: scroll and zoom a captured tab](https://developer.chrome.com/docs/web-platform/captured-surface-control) |
| **Optional Capture Handle cooperation** | A captured page can opt in to expose its origin and a caller-provided string `handle`; the capturing page can read updates when permitted. A cooperating page could encode its own application state in that handle. | It requires changes to the captured page and an explicit origin allowlist/configuration. It is not a general browser facility that reads arbitrary pages' URL, scroll offset, or document height. The W3C document is a Working Draft. [W3C Capture Handle](https://www.w3.org/TR/capture-handle-identity/) |
| **Browser extension** | A Chrome extension can capture the active tab's visible pixels with `tabs.captureVisibleTab()`, and can inject a content script to read page values such as `location.href`, `window.scrollY`, and `document.documentElement.scrollHeight`. | Requires extension installation. `captureVisibleTab()` requires `activeTab` or `<all_urls>` permission; programmatic content-script injection additionally uses `scripting` plus access to the target origin (for example temporary `activeTab` access). Chrome documents `captureVisibleTab()` as expensive and limits it to two calls per second. `window.scrollY` is the top-level viewport offset; inner scrolling elements need their own `scrollTop` measurement. Content scripts normally target the top frame; `all_frames` injects only into frames that also match the URL requirements; a top-frame script cannot read a cross-origin iframe's DOM, though an extension may inject a separate script into a matching frame with the needed access. [Chrome `tabs` API](https://developer.chrome.com/docs/extensions/reference/api/tabs), [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [WHATWG same-origin policy](https://html.spec.whatwg.org/multipage/origin.html#same-origin) |
| **Controlled browser automation** | A browser session owned by the application or test harness can evaluate page state (`location.href`, scroll values, document height) and save viewport or full-page screenshots. Playwright documents both `page.evaluate()` and `page.screenshot({ fullPage: true })`. | This applies when the app controls or launches the browsing session. It changes the interaction model from observing a user's normal browser share to operating a controlled browser. It is useful for deterministic demos and fixtures, not as metadata from an arbitrary shared tab. [Playwright page evaluation](https://playwright.dev/docs/evaluating), [Playwright screenshots](https://playwright.dev/docs/screenshots) |

## Recommendation for the slow research demo

Keep the current human-operated shared-tab stream. Sample its video pixels with the existing video-and-canvas path, wait for a short stable interval after visible changes, and retain only a new non-duplicate candidate. Adjacent-frame overlap can help relate nearby viewport captures, but store it as an estimate rather than an absolute source offset. This preserves natural browsing without OCR or page instrumentation.

Keep the controlled `44`→`45` change as a small-change acceptance case: if the digit changes in source pixels, the settled capture path must retain a candidate even when the change occupies only a small part of the viewport. The v2 protocol already names that exact controlled scenario and asks for the source-stream PNG and thumbnail before/after pairs. [Automatic capture v2 protocol](./automatic-capture-v2/PROTOCOL.md)

Do not add model concurrency for this demo. The research question is whether slow pixel capture can preserve useful distinct views and small visible changes; the existing queued model path can continue to wait for one image to finish and then re-evaluate.

## Source status and limits

This note uses current W3C specifications and first-party Chrome and Playwright documentation.
