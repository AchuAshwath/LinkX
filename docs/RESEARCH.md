# Research: AI Agents and the Jurisdictional Boundaries of Platform ToS

> **Status:** Working draft
>
> **Context:** This document is the research core of LinkX. It analyzes how platform Terms of Service define "automation" and where those definitions break down when AI agents operate outside the platform's technical boundary.

---

## Abstract

Social media platforms prohibit automation through Terms of Service clauses that target interface access methods — "bots, scrapers, crawlers, or any other automated means." These rules were written to catch deterministic scripts that interact with a platform's DOM or API. However, the emergence of vision‑language AI agents creates a new category of tool that can observe a platform's rendered output (via screen capture) and generate platform‑directed content without ever touching the platform's technical infrastructure. This project implements a direct browser automation system (System A) as a control case, and proposes a screen‑observation architecture (System B) as the experimental case, to demonstrate that current ToS frameworks contain a jurisdictional gap that will widen as vision models improve.

---

## 1. Introduction

The rise of AI agents capable of "computer use" — reading screens, understanding UI layouts, and generating actions — is dissolving the boundary between human and automated interaction with web platforms. Tools like Anthropic's Claude computer use, OpenAI's GPT‑4V, and open‑source frameworks like `browser-use` can dynamically analyze a webpage and produce context‑specific actions without pre‑written scripts.

This raises a question that platform policy teams haven't addressed:

> If an AI agent looks at your screen, thinks about what it sees, and tells you what to type — but never touches the platform's code, network, or DOM — is that "automation"?

LinkX was built to explore this question. It implements the traditional approach (System A: browser automation) and is designing the alternative (System B: screen observation) to produce a comparative analysis.

## 2. Background

### 2.1 Evolution of Anti‑Bot Language

Platform ToS language has evolved through three generations:

| Era | Language Pattern | What It Caught |
|-----|-----------------|----------------|
| 2005–2012 | "No scripts or bots" | Static Python scripts, cURL abuse |
| 2012–2020 | "No automated tools or software" | Selenium, Puppeteer, browser extensions |
| 2020–present | "No bots, scrapers, crawlers, or **any other automated means**" | Everything — including dynamic AI agents |

The current generation of ToS language uses catch‑all phrasing ("any automated means," "any software that accesses") specifically designed to be technology‑agnostic. This was a smart policy decision that closed the loophole around increasingly sophisticated automation tools.

But it also created an over‑broad boundary that, if enforced literally, would cover screen readers, accessibility tools, and clipboard managers.

### 2.2 Technical Taxonomy

Not all "automation" touches the platform in the same way:

| Level | Method | Platform Contact | Example |
|-------|--------|------------------|---------|
| **L1: API access** | Official REST/GraphQL endpoints | Direct, authorized | LinkedIn Marketing API |
| **L2: DOM automation** | Browser controlled via CDP/WebDriver | Direct, unauthorized | Playwright, Selenium |
| **L3: Input injection** | OS‑level keyboard/mouse simulation | Indirect | AutoHotKey, AppleScript |
| **L4: Observation** | Screen capture + OCR/VLM analysis | None | HDMI capture, screencapture |

Current ToS clauses clearly cover L1–L2. L3 is ambiguous (accessibility tools live here). L4 is unaddressed — the platform has no technical awareness that it's happening.

## 3. Comparative ToS Analysis

### 3.1 Clause‑by‑Clause Breakdown

#### LinkedIn User Agreement (Section 8.2)

> "You will not … use bots, scrapers, crawlers, or any other automated means to access the Services, add or download contacts, or send or redirect messages."

| Does it cover... | Verdict | Reasoning |
|------------------|---------|-----------|
| Playwright reading the DOM | ✅ Yes | "automated means to access the Services" |
| API client without authorization | ✅ Yes | "automated means to access" |
| Screen capture + OCR | ❌ No | Screen capture doesn't "access the Services" — it accesses your local display buffer |
| AI reading a video feed of your desktop | ❌ No | The AI accesses a video stream, not the service |

#### X Developer Guidelines

> "Non‑API automation (scraping, browser automation) results in permanent suspension. Always use the official X API."

| Does it cover... | Verdict | Reasoning |
|------------------|---------|-----------|
| Playwright / Selenium | ✅ Yes | Explicitly named: "browser automation" |
| Dynamic code generated by AI per‑action | ✅ Yes | Still "browser automation" regardless of how the code was written |
| AI reading screen capture | ❌ No | Not "Non‑API automation" — no automation touches their infrastructure |

> "Don't automatically post about trending topics."

| Does it cover... | Verdict | Reasoning |
|------------------|---------|-----------|
| Bot reads trending → auto‑posts | ✅ Yes | Explicit prohibition |
| AI reads screen → drafts in text editor → human posts | ❓ Gray | Content creation was automated; the posting was human. Is the "automation" the writing or the posting? |

#### Meta Platform Terms (Section 3.2)

> "You will not engage in automated data collection without our permission."

| Does it cover... | Verdict | Reasoning |
|------------------|---------|-----------|
| Scraping via DOM | ✅ Yes | "automated data collection" |
| Reading a video feed of your own screen | ❌ Ambiguous | Is OCR on your own display "data collection from" their platform? |

### 3.2 The Pattern

Every platform defines the violation boundary at the **technical interface** — accessing their services, their API, their DOM, their network layer. None of them claim jurisdiction over what you do with pixels already rendered on your screen.

## 4. System A: Browser Automation (Control Case)

System A is fully implemented in this repository. It uses Playwright (via `rebrowser-playwright`) to directly control a Chromium browser, interacting with platform DOM elements.

### 4.1 Architecture

See [`docs/specs/browser-engine.md`](./specs/browser-engine.md) for the full spec. Key components:

- **BrowserManager**: Persistent sessions via real Chrome login (cookies + localStorage + IndexedDB)
- **EvasionMouse**: Bézier curve mouse movement, idle wiggling, click jitter
- **humantyping**: Realistic keystroke simulation (IKI log‑normal, Markov fatigue, QWERTY neighbor typos)
- **rebrowser-playwright**: Patched Chromium that suppresses CDP `Runtime.enable` signal
- **3‑tier self‑healing**: Hardcoded selectors → AI agent fallback → human alert

### 4.2 Forensic Profile

Despite sophisticated evasion, System A leaves artifacts:

| Artifact | Present? | Notes |
|----------|----------|-------|
| CDP connection | ✅ Yes (masked) | `rebrowser-playwright` suppresses but doesn't eliminate |
| `navigator.webdriver` | ❌ No (overridden) | Stealth injection removes this signal |
| Behavioral anomaly | ⚠️ Low | Bézier curves + jitter pass basic analysis |
| TLS fingerprint mismatch | ❌ No | Real Chromium engine = natural fingerprint |
| Session pattern anomaly | ⚠️ Low | Persistent contexts mimic real user sessions |
| Network origin anomaly | Depends | Residential IP = safe; datacenter IP = flagged |

### 4.3 ToS Verdict

**System A violates platform ToS** — full stop. The evasion techniques reduce *detection probability* but don't change the *legal classification*. Whether the code was written by a human three months ago or generated by an LLM 0.5 seconds ago, executing it via a browser automation framework makes it an "automated means to access the Services."

See [`docs/specs/evasion-strategy.md`](./specs/evasion-strategy.md) for the complete evasion analysis.

## 5. System B: Screen Observation (In Planning)

> **Status:** 💡 Planning / ideation. Architecture spec to be written.

System B is designed to operate **entirely outside the platform's technical boundary**. It would demonstrate that an AI agent can extract information from and generate content for a platform without ever triggering a ToS violation — because it never "accesses" the platform.

### 5.1 Conceptual Architecture

```
┌─────────────────────┐
│  Browser (normal,   │     ┌─────────────────────┐
│  no automation      │────▶│  Your Screen         │
│  hooks attached)    │     │  (rendered pixels)   │
└─────────────────────┘     └──────────┬──────────┘
                                       │
                              screen capture / video feed
                              (macOS screencapture, OBS,
                               HDMI capture card)
                                       │
                                       ▼
                            ┌─────────────────────┐
                            │  AI Vision Agent     │
                            │  (VLM + OCR)         │
                            │                      │
                            │  Reads flat pixels   │
                            │  Never touches DOM   │
                            │  Never calls API     │
                            └──────────┬──────────┘
                                       │
                                       ▼
                            ┌─────────────────────┐
                            │  Staging Area        │
                            │  (text editor,       │
                            │   LinkX dashboard)   │
                            │                      │
                            │  Content drafted     │
                            │  in isolation        │
                            └──────────┬──────────┘
                                       │
                              human reviews draft,
                              manually posts
                                       │
                                       ▼
                            ┌─────────────────────┐
                            │  Human Action        │
                            │  (copy-paste, type,  │
                            │   or click "Post")   │
                            └─────────────────────┘
```

### 5.2 Three Variants Under Consideration

**Variant A — Pure Staging Area** (Strongest legal position)
- AI reads video feed, drafts content in a text editor
- Human manually copies the text and posts it on the platform
- Zero software contact with the platform at any point

**Variant B — Human‑Mediated Input** (Operational gray area)
- AI reads screen, generates content, moves cursor to "Post" button
- Script pauses — human must physically click to authorize
- The final network packet is initiated by a biological human action

**Variant C — Accessibility Framework Routing** (Technical gray area)
- AI routes input through the OS accessibility API (macOS Accessibility, Windows UI Automation)
- Platform can't distinguish this from a screen reader user
- Blocking it risks violating digital accessibility law (ADA, EU Accessibility Act)

### 5.3 ToS Verdict (Projected)

| Variant | Touches Platform? | ToS Violation? | Detection Feasible? |
|---------|-------------------|----------------|---------------------|
| A — Staging | No | No | No |
| B — Human click | Human does | Ambiguous | Very hard |
| C — Accessibility | Via OS API | Ambiguous | Hard (risks ADA conflict) |

## 6. The Jurisdictional Gap

### 6.1 Why Platforms Can't Close This Gap

If a platform tried to extend its ToS to cover screen observation — for example:

> "You may not use any software to observe, interpret, or analyze any visual rendering of our platform."

This would:

1. **Criminalize screen readers** for visually impaired users → direct conflict with the Americans with Disabilities Act and EU Accessibility Act
2. **Criminalize screenshots** → absurd and unenforceable
3. **Claim ownership of rendered pixels on your hardware** → conflicts with consumer device rights and first‑sale doctrine analogues
4. **Prohibit note‑taking apps** that use OCR → collateral damage to legitimate tools

Platforms are stuck in a regulatory bind. They can't extend their ToS to cover *observation of your own screen* without creating legal conflicts far larger than the automation problem they're trying to solve.

### 6.2 Detection vs. Legality

These are separate questions:

| | Detectable? | ToS Violation? |
|---|---|---|
| System A: Browser automation | Yes (with effort) | Yes |
| System B‑A: Staging area | Undetectable | No |
| System B‑B: Human‑mediated click | Very hard | Ambiguous |
| System B‑C: Accessibility API | Hard | Ambiguous |

Something being **undetectable** doesn't make it **compliant**. But something being **undetectable AND not covered by any ToS clause** represents a genuine policy gap.

### 6.3 Relevant Case Law

**hiQ Labs v. LinkedIn (9th Circuit, 2022)** — The court ruled that scraping publicly visible data did not violate the CFAA. The principle: if data is rendered for you to see, the act of looking at it (even with software) occupies different legal ground than unauthorized access.

While hiQ concerned web scraping (which still touches the platform's servers), the underlying logic extends to screen observation, which doesn't touch the platform's servers at all.

## 8. Discussion

### 8.1 The Observation Boundary

The central finding of this research is that platform governance models assume a **technical boundary** that coincides with their enforcement boundary. They can detect and block software that touches their DOM, API, or network layer. But they have no mechanism to detect — or ToS clause to prohibit — software that reads a video feed of pixels already rendered on a user's own device.

This gap will widen as vision‑language models improve. Today, VLMs require significant compute and cost to analyze screen frames. Within 2–3 years, local models running on consumer hardware will be able to do this in real time.

### 8.2 Policy Recommendations for Platforms

1. **Shift from access‑based to outcome‑based definitions**: Instead of "don't use automated means to access," define prohibited *outcomes* (e.g., "don't post content generated without human editorial judgment" or "don't scrape and republish trending topics at scale").
2. **Behavioral detection at the content layer**: Detect automation by analyzing *content patterns* (posting frequency, topic alignment with trends, stylistic uniformity) rather than *input signals* (WebDriver flags, CDP connections).
3. **Acknowledge the accessibility constraint**: Any enforcement mechanism must explicitly exempt OS accessibility frameworks to avoid legal exposure.

### 8.3 Ethical Implications

Documenting a gap in a defensive system creates a dual‑use risk. This is analogous to security vulnerability disclosure — publishing the finding helps platforms improve their governance models, but it also provides a roadmap for bad actors. We've chosen open documentation because:

- The gap is not a secret — anyone who reads the ToS carefully can identify it
- Platform policy teams need specific, technical analysis to close it
- Keeping it private doesn't prevent exploitation; it just delays informed policy responses

See [`ETHICS.md`](../ETHICS.md) for our full ethical framework.

## 10. Conclusion

This project demonstrates two things:

1. **System A proves a positive**: Platform ToS clauses effectively catch browser automation, regardless of evasion sophistication. The "any automated means" language is well‑drafted for its intended purpose.

2. **System B reveals a gap**: Current ToS frameworks cannot reach AI systems that operate entirely outside the platform's technical boundary. This isn't a bug to exploit — it's a structural limitation that platform policy teams should address before vision‑language models make observation‑based agents trivially easy to build.

The question isn't whether someone *will* build a System B. It's whether platforms will update their governance models before it becomes mainstream.
